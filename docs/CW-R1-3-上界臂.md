## 1 `ORACLE-KNOWN` 是什么，以及它**为什么必须越界**

### 1.1 越界的精确边界

| 特权 | 策略本来能怎么做 | 上界臂怎么做 | 越界幅度 |
|---|---|---|---|
| 信道真值 `log h_t` | 花 `c_probe=1` 量子做 `PROBE(i)`，读一个 `N(log h_i, σ_csi²)` 的样本 | **直接读** `world._log_h_true` | 省掉每次 1 量子；省掉 `σ_csi=0.05` 的噪声 |
| 状态真值 `\|x_t\|` | 只能靠**送达的帧**更新接收端 `x_hat` | **直接读** `world._x_true` | 省掉 `σ_meas=0.2` 的采样噪声；省掉"必须送到"这一步 |
| 模型参数 | 全部已知（协议设定） | 同 | 无 |

越界走**显式白名单**：`run_episode(allow_truth_keys=True)` + `OracleKnown.attach_truth(world)`。**不**经 `view._inner`（那是 R0 反例 1 判死的通道，`SchedulerView.__getattr__` 会抛）。

### 1.2 为什么"读到 `|x_t|`"**不额外送钱**——这是本篇唯一需要读者复核的推导

帧的边际价值（推导见 §2）：`ΔV(x) = κ·(√(x²+P) − √(x²+P(1−f)))`，`κ=½(q+rK²)=0.5717`、`P=1.0193`、`f=P/(P+σ_meas²)=0.9622`。
它对 `x` 的敏感度 `∂ΔV/∂x = κ·x·(1/√(x²+P) − 1/√(x²+P(1−f)))` 在 `x ≲ √P ≈ 1.01` 时最大 **≈ 0.45/单位 x**。
而**完整模型**给出的后验误差 `√P ≈ 1.01` ⇒ 估值误差带来的值估计噪声最多 **≈ 0.45**，与 `HOLD` 的每槽成本 `0.0891` 同量级。

> ★ **段首这几句在 §4.2 被实测推翻了一半**：我们以为"精度不是来源"，实测发现
> "**知道 `|x_t|`**"不但不加钱，反而是**负价值**（`no_x` 变体更便宜 0.0466 < 0.0653）。
> 原因是 `ΔV(x)` 的斜率（`x` 从 0 到 0.35 只降 17%）**远小于** `p(log h)` 的斜率（`log h` 从 0 到 1.9 使 `p` 从 0.5 到 0.97），
> 于是"挑 x"会把"挑信道"的排序搅乱。**这段推导保留原文**，作为"先验推理被实测否证"的记录。

## 2 决策规则（一次写定，看结果之前）

### 2.1 从 LQR 扰动推出"一帧值多少"

设 `x_{t+1} = A x_t + B u_t + w_t`，`u_t = −K x̂_t`，`x̂` 为接收端估计。
记偏差 `u_t := x_t − x̂_t`。在 `A=1` 的 BOUNDED plant 上 `u_{t+1} = u_t + w_t`（**系数 1**）。
`u_t` 已知时的阶段成本 `q x_t² + r u_t²` 对**偏差**展开（`x̂` 与 `u` 同号时是下界）：

    cost(u_t) ≃ q x̂_t² + 2q x̂_t·u_t + (q + rK²)·u_t²

于是**在 t 槽发出并送达** ⇒ `u_t ← 0` ⇒ 省下 `2q x̂_t u_t + S·u_t²`（`S := q + rK²`）；
**不送达** ⇒ 保留该量，且下一槽 `Var(u) += σ_w²`。对 `u_t ~ N(0, P)` 取期望、对半取中（平方项的一阶近似）：

    ΔV(x) ≈ κ·( √(x² + P) − √(x² + P(1−f)) ),  κ = ½S,  f = P/(P+σ_meas²)

`√(x²+P) − √(x²+P(1−f))` 正是偏差的 RMS：从 `√P` 降到 `√(P(1−f))`。

### 2.2 规则

    v_send(i) = p_i · ΔV_i(x_i)            p_i = sigmoid(κ_ch·(log h_i − log h*))  ← 真信道
    v_hold    = 0
    v_probe(i) = 0                          ← 全知臂已经知道 log h

    a* = argmax{ v_send(i), 0 }，余额 < c_data ⇒ HOLD

**`v_probe ≡ 0` 是设计选择**：它把"探测"这条通道在**主臂**上关死。
**这个选择是否遗漏了什么，由 `OracleKnownProbeable` 检验**（§4.3）。

## 5 为什么输：三条实测，不是推测

### 5.1 它挑了**对的人**，输在**发的次数**

| 臂 | 预算 | 实际发送 | 中位成本 | 选中对的用户 | 选错 | Σ(logh[u]−logh[1−u]) |
|---|---|---|---|---|---|---|
| `periodic4` | 64 | 64 | 0.027045 | 28 | **32** | −3.40 |
| `ORACLE-KNOWN` | 64 | 64 | 0.089270 | **56** | **6** | **+62.59** |
| `ORACLE-KNOWN` | 128 | 128 | 0.036962 | **108** | 15 | **+117.95** |
| `periodic1` | 128 | 128 | 0.045344 | — | — | −4.43 |

（ep100，ρ0.85，逐槽对比两个用户的真 `log h`；`Σ` 行 = 每次 SEND 时"所选用户 − 另一用户"的 `log h` 差之和。）

**同上预算 64**：上界臂选对的 **56/64**、`periodic4` 只有 **28/64** —— **上界臂的"挑谁"远好于轮转**。
但它仍然**贵 3.3 倍**（0.0893 vs 0.0270）。
**同预算 128**：上界臂 0.036962，**优于** `periodic1` 的 0.045344（−18.5%）——**它赢**。

⇒ 结论：**上界臂的规则没有错在"挑谁"，错在"多久发一次"**。它的 `ΔV` 几乎不随"多久没发"下降（§5.2），
所以它"有钱就发满"；而 `periodic4` 只花一半预算就达到更低成本。

★ **但这两行也说明了反方向的事实**：同预算 128 时上界臂 **0.036962 优于 `periodic1` 的 0.045344（−18.5%）**。
故"上界臂在挑谁上更聪明"是**被证实**的（同预算 64：56/64 vs 28/64；同预算 128：−18.5%）；
它的失败在**预算分配**（发满 vs 只发 1/4）。§5.3 与 §6.1 会说明为什么这不是"再调一个参数就能修"的问题。

### 5.2 `ΔV` 与"多久没发"几乎无关 —— 这是本协议的结构性质

`u_{t+1} = u_t + w_t`（§2.1，`A=1`），所以**每槽不发，`Var(u)` 只涨 `σ_w² = 4e-4`**；
而 `P ≈ 1` ⇒ 16 槽不发只把 `P` 从 1.0 推到 1.0064（**+0.64%**）。

| 帧间隔 k 槽 | 不发时的 P_k | 一帧后 P | ΔP |
|---|---|---|---|
| 1 | 1.000400 | 0.033145 | 0.967255 |
| 4 | 1.001600 | 0.033184 | 0.968416 |
| 16 | 1.006400 | 0.033343 | 0.973057 |
| 32 | 1.012800 | 0.033555 | 0.979245 |

⇒ **一帧的价值几乎与"它多陈旧"无关**（`ΔP` 从 0.967 到 0.979，差 1.2%）。
于是"该不该发"的答案在任意 `|x|` 下都接近"该"，**机会成本才是唯一约束**。

**这正是 `periodic4` 便宜 3.3 倍的原因**：它靠"少发"省钱，而"少发"在这个 plant 上**几乎不付代价**。

### 5.3 发送的机会成本 > 它的收益（在低预算档）

- 一帧的价值：`|x| ∈ [0.17, 0.35]`（实测 `HOLD` 下的 `|x|` 中位 0.169、p90 0.353）时 `ΔV ∈ [0.419, 0.505]`。
- 机会成本：`204` 量子发 204 帧 vs `periodic4` 的 64 帧 ⇒ 多出的 140 帧，每帧挤掉的是"下一个可用于
  其他用户/其他槽的帧"。
- **`B/T=0.8` 档的 `att = 204`**（几乎每槽一帧）：`periodic1` 在同一预算下 0.035498 而 `periodic4` 在
  0.8 档仍是 **0.047678 且只用 64 量子**（与 0.5 档**逐位相同**，见 §6.1）⇒ **多花 140 量子反而更贵**。

★ **这不是"发得越多越差"的一般结论**：`B/T=0.5` 档上界臂 0.0653 > `periodic4` 0.0477，
而 `B/T=0.8` 档上界臂 0.0453 < `periodic4` 0.0477 —— **同一臂在两档之间自身就翻转了**。

## 6 反向核查：这一轮有没有可能是"我自己写错了"

### 6.1 一个必须记录的事实：`periodic4` 对预算**完全不敏感**

`periodic4` 在 B=128 与 B=64 下**逐 episode 逐位相同**（12/12，差 `+0.00e+00`，`budget_used` 恒 64）。
原因：`PeriodicBaseline` 每 4 槽发一次 ⇒ 256 槽最多 64 帧 ⇒ **B ≥ 64 对它不是约束**。

⇒ **"同预算"比较在 `B/T ≥ 0.25` 时对 `periodic4` 没有意义**：它永远只花 64。
⇒ 上界臂"花满 128/204"是**它自己的选择**，不是协议的强制。**这一点削弱了 §5.3 的机会成本论证**：
   上界臂完全可以像 `periodic4` 一样只发 64 帧 —— 它没有，是因为规则里"有钱就发"。

### 6.2 K1/K2 的通过**不能**用来支持"规则是对的"

K1/K2 只证明"特权接线了"（关掉必变），**不证明"特权被用对了"**。
§4.2 的 `no_x` 更便宜恰恰说明：**接线成功 ≠ 用得对**（教训 #39 + R12 的同一条）。

### 6.3 本轮自己的三处错误（写在交付里，不埋在代码注释里）

| # | 错误 | 发现方式 | 影响 |
|---|---|---|---|
| 1 | `OracleKnownProbeable` 把 100% 预算烧在探测上 | K3 打印 `probe=128/204`、`attempted=0` | 该变体的 4 行**全部作废**，不得引用 |
| 2 | 早先量级脚本把 `P_ss` 写成 `1.0385`（用了错误的 `alpha = 1−P/(P+σ²)`），真值 `1.0193` | 与 `run_episode` 实测 `cost_by_user` 对账 | 帧价值表整体偏小 ~2%；§5.3 已用 1.0193 重算 |
| 3 | 早先误以为 `theta_det = L²/(r+B²P)` 中 `L=K`，实际 `A·B·P/(r+B²P)` 才是 `K` | 逐位打印 `L/K = 1.000000000000` 对账 | 只影响过程稿，未进任何结论 |

★ 另有一处**未修但必须点名**的数值隐患：`CWWorld.__init__` 里 `_log_h_true = zeros`，
**信道真值一律从 0 起步**（而 `h_log_init_std=1.0` 只被用作**信念**初值）。
后果：`ρ=0.98` 时 AR(1) 的时间常数 ≈ 49 槽，256 槽里 `log h` 只在 −1.16…+0.77 之间移动
（稳态 sd 应为 5.03）⇒ **信道在两档 ρ 之间的差异被压缩**。
本轮**不改**（改它要重跑 R0/R1-1/R1-2 全部证据）；但**所有跨 ρ 的比较都必须带上这句**。

## 7 判词的原样措辞（面试/文档引用时抄这一段）

> 在 CW-POMDP-v1（N=2、T=256、B ∈ {128, 204}、BOUNDED plant、外生 AR(1) 信道）上，
> 我们构造了**全知模型 + 全知信道**的上界调度臂（读真 `log h` 与真 `x`，经 `allow_truth_keys` 白名单）。
> 预注册判据（4 格中 ≥ 3 格：中位成本比 < 0.9 且逐 episode 胜率 ≥ 0.7）**未通过**：
> 4/4 格比值达标（0.47–0.78）但胜率均 ≤ 0.25。判 **`SPACE-VOID`**。
> 机制上：该臂在**同预算**下"挑对用户"的比例（56/64）远超轮转基线（28/64），
> 但**发得太多**（128/204 帧 vs 64 帧），而在这个 plant 上"少发"几乎不付代价
> （每槽不发只让后验方差涨 `σ_w²/P = 0.04%`）。
> **这一判词限制的是该协议与该 plant 的信息结构，不构成"学习方法无效"的证据。**
